## 16:14 — Validation strategy: outlier mocks vs posterior sharpness
**Topics:** Validation tab interpretation, mock CDF realisations, posterior behaviour under outlier draws, planned representative-vs-outlier comparison experiment
**Work done:**
- Discussion-only session — no code edits. User externalised reasoning for the validation experiment design they want to run with the new batch-mock button.
**Decisions / understanding captured:**
- Each Validation seed produces one CDF realisation drawn from the "true" distribution defined by the current mock parameters. The point of running N mocks is to see the CDF *distribution* visually, not just a single realisation.
- Outliers are only identifiable when compared to the known underlying distribution. In real observational data we cannot tell whether the observed CDF is typical or an outlier — that's the core inference risk.
- The simulation reports the most-likely distribution per realisation; because outliers from distribution A overlap with typical draws from distribution B, the recovered "best" parameters can land on the wrong distribution. The full per-model likelihood is kept precisely so the posterior over parameters can express that uncertainty.
- Planned experiment: per separation regime (easy / medium / hard blend of singles vs binaries CDFs), run **3 sub-cases × 2 outlier mocks**, one outlier from each tail of the σ. Compare to a representative-mock pass.
- Success criterion: posteriors should be *sharp* on representative mocks (centered on truth) and *wide* on outlier mocks while still containing the true parameters in the corner plot. That would confirm the inference behaves honestly.
- Failure criterion (and what to worry about): if posteriors stay sharp under outlier mocks, the simulation will report a confident wrong answer when real data happens to be an outlier — no internal flag would catch it. User will need to rethink the inference layer in that case.
- Next implementation step (deferred): a button for "run N mocks" instead of clicking through one-by-one in the current GUI (note: the 16:13 entry already added this — user's note here pre-dates seeing the new control land; they may have been thinking of an even more batched workflow).
